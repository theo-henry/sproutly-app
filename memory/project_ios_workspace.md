There is now a third native workspace at `ios/` alongside `android/` and the
frozen web app at the repo root. It is a pure SwiftUI app targeting iOS 16+
that mirrors the Android module-by-module: `Auth/`, `Home/`, `Products/`,
`Nearby/`, `Recipes/`, `MealPlan/`, `Profile/`, `Scanner/`, `Navigation/`,
`Core/Design/`.

**Why:** the user asked for an iOS equivalent of the Android app to ship as a
downloadable artifact on the landing page. The Android project is native
Kotlin/Compose (not Flutter), so direct Flutter-style platform sharing was not
possible — the chosen path was a native SwiftUI rewrite.

**How to apply:**

- Default new iOS code to `ios/Sproutly/<Module>/`. Do not put iOS code inside
  `android/`. Do not put Android code inside `ios/`.
- Xcode project is generated by XcodeGen from `ios/project.yml`. The
  `.xcodeproj` is gitignored. Run `xcodegen generate` after editing
  `project.yml`.
- Zero external dependencies on purpose — CI build stays trivial. If you need
  the Supabase Swift SDK, add it under `packages:` in `project.yml` and update
  the README.
- CI workflow lives at `.github/workflows/ios.yml`; it produces an
  `Sproutly-unsigned.ipa` artifact on `macos-14` via `xcodebuild archive` with
  `CODE_SIGNING_ALLOWED=NO`. Unsigned IPAs are downloadable but not directly
  installable on a stock iPhone — TestFlight / paid Apple Developer signing is
  required for that.
- Auth and meal-plan generation are local stubs with clear seams for hooking
  Supabase later. Do not add API keys to the Swift client; route via the
  existing Supabase Edge Functions (same model as Android).
